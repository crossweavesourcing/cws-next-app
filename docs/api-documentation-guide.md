# API Documentation Guide

How the CWS Next App's automated API documentation system works, and how to maintain it.

## How the System Works

Every API route must co-locate an `openapi.ts` file alongside its `route.ts`:

```
src/app/api/health/
  route.ts      ← HTTP handler
  openapi.ts    ← Zod schemas + OpenAPI path object
```

At build time (`pnpm docs:generate`), all 20 path objects are imported by `src/lib/api/assemble.ts` and merged into a single OpenAPI 3.1.0 document written to `public/openapi.json`.

CI enforces that every exported HTTP method handler (`GET`, `POST`, etc.) in every `src/app/api/**/route.ts` file has a corresponding entry in the generated spec. Undocumented routes are rejected.

## Creating a New Documented Route

### 1. Create the route handler

```ts
// src/app/api/items/route.ts
import { NextResponse } from 'next/server';

export async function GET(request: Request) {
  // ...
  return NextResponse.json({ items: [] });
}
```

### 2. Create the OpenAPI definition

```ts
// src/app/api/items/openapi.ts
import * as z from 'zod/v4';
import { createSchema } from 'zod-openapi';
import { TAGS } from '@/lib/api/tags';

export const ItemSchema = z.object({
  id: z.string().meta({ description: 'Item ID', example: 'abc123' }),
  name: z.string().meta({ description: 'Item name', example: 'Widget' }),
});

export const itemsPath = {
  '/api/items': {
    get: {
      operationId: 'listItems',          // unique, required
      summary: 'List all items',          // required
      description: 'Returns all items.',
      tags: [TAGS.GENERAL],               // required, at least one
      security: [{ cookieAuth: [] }],     // omit for public
      responses: {
        '200': {                           // at least one response required
          description: 'List of items',
          content: {
            'application/json': {
              schema: createSchema(z.array(ItemSchema)).schema,
            },
          },
        },
      },
    },
  },
};
```

### 3. Wire into assemble.ts

```ts
// src/lib/api/assemble.ts
import { itemsPath } from '@/app/api/items/openapi';

// In assembleOpenApiDocument(), add to the mergePaths() call:
  itemsPath as Record<string, unknown>,
```

### 4. Regenerate and verify

```bash
pnpm docs:generate
pnpm docs:lint
pnpm docs:coverage
```

## Defining Request and Response Schemas

**Zod v4 + zod-openapi** is the schema library. Define schemas with `zod/v4`, convert to OpenAPI JSON Schema with `createSchema()`:

```ts
import * as z from 'zod/v4';
import { createSchema } from 'zod-openapi';

const MySchema = z.object({
  field: z.string().min(1).max(100).meta({
    description: 'Field description',
    example: 'example value',
  }),
});

// Use in responses:
createSchema(MySchema).schema

// Use for individual fields (parameters):
createSchema(MySchema.shape.field).schema
```

### Nullable fields

OpenAPI 3.1.0 does not support `nullable: true`. Use union types:

```ts
z.string().nullable().meta({ example: 'value' })
// Generates: { type: ['string', 'null'] }
```

### Reusable schemas

Place shared schemas in `src/lib/api/`:

| File | Purpose |
|---|---|
| `errors.ts` | `ErrorSchema`, `ValidationErrorSchema`, `UnauthorizedSchema`, `NotFoundSchema`, etc. |
| `primitives.ts` | `ObjectIdSchema`, `IsoDateTimeSchema` |
| `pagination.ts` | `PaginationQuerySchema`, `createPaginatedSchema()` |
| `security.ts` | `SECURITY_SCHEMES` constant |
| `tags.ts` | `TAGS` constants |
| `models/user.ts` | `UserProfileResponseSchema` |

## Documenting Authentication

Reference security schemes from `src/lib/api/security.ts`:

```ts
security: [{ cookieAuth: [] }],      // Session cookie (web)
security: [{ bearerAuth: [] }],      // JWT bearer (mobile)
security: [{ cookieAuth: [] }, { bearerAuth: [] }],  // Either
security: [],                        // Public (no auth)
```

## Path Parameters

Next.js dynamic segments translate to OpenAPI path parameters:

| Filesystem | OpenAPI path |
|---|---|
| `[id]` | `{id}` |
| `[...slug]` | `{slug}` |
| `[[...slug]]` | `{slug}` |
| `(group)` | removed |

## Excluding Routes

Routes that should not appear in the OpenAPI spec (e.g., OPTIONS handlers) must be added to the `EXCLUDED_ROUTES` array in `src/lib/api/assemble.ts` with a documented reason:

```ts
{
  method: 'OPTIONS',
  path: '/api/mobile/v1/auth/me',
  reason: 'CORS preflight handler — automatically generated by mobile middleware',
  category: 'cors-preflight',
  securityVisibility: 'public',
  whyInappropriate: 'OPTIONS handlers return CORS headers with no body...',
},
```

Exclusions without a reason will fail the coverage check.

## Running Documentation Locally

```bash
# Generate the OpenAPI spec
pnpm docs:generate

# Lint the spec with Redocly
pnpm docs:lint

# Check route coverage (are all routes documented?)
pnpm docs:coverage

# Run all checks in sequence
pnpm docs:check

# Validate API contracts
pnpm test:api-contract

# Start dev server with docs
pnpm docs:dev
```

## Regenerating OpenAPI

After any change to `openapi.ts` files or `assemble.ts`:

```bash
pnpm docs:generate
```

This writes `public/openapi.json`. Commit the generated file — CI checks for drift.

## Running CI Checks Locally

```bash
# Full documentation integrity check (runs generate, stale, lint, coverage, contract)
pnpm docs:check

# Individual checks
pnpm docs:generate
npx tsx scripts/check-stale-openapi.ts
pnpm docs:lint
pnpx tsx scripts/check-route-coverage.ts
npx tsx scripts/check-contract.ts

# Full build validation (what CI runs)
pnpm docs:generate && pnpm lint && npx tsc --noEmit && pnpm test:unit && pnpm build
```

## Approving Intentional Breaking Changes

Breaking change detection runs automatically on pull requests. If you intentionally introduce a breaking change:

1. Review the breaking changes report in the CI artifacts
2. Document the change in the PR description with:
   - What is breaking
   - Why it is necessary
   - Migration steps for consumers
   - Timeline for deprecation
3. Get approval from a code owner
4. Merge with the breaking change

The breaking change detector identifies:
- Removed operations
- Removed response fields
- Newly required request properties
- Narrowed enum values
- Parameter type changes
- Authentication requirement changes
- Removed status codes
- Incompatible response schema changes

## Troubleshooting Failures

### "Implemented route X is missing from OpenAPI document"

The route handler exports an HTTP method that has no corresponding entry in the OpenAPI spec. Fix: create an `openapi.ts` file and wire it into `assemble.ts`.

### "OpenAPI operation X has no corresponding route handler"

The OpenAPI spec documents an operation that no longer exists in the route handler. Fix: remove the stale entry from the path object in `openapi.ts`.

### "operationId is missing"

Every operation must have a unique `operationId`. Add one to the path object.

### "Duplicate operationId"

Two operations share the same ID. Each operation must have a unique ID.

### "OpenAPI artifact is stale"

The committed `public/openapi.json` doesn't match what the current source would generate. Fix: run `pnpm docs:generate` and commit the result.

### "Exclusion has no reason"

An entry in `EXCLUDED_ROUTES` is missing its `whyInappropriate` or `reason` field. Every exclusion must justify why it is excluded.

### Redocly lint warnings

Warnings (not errors) for missing license, localhost URLs, or missing 4XX responses are acceptable for this private API. Errors must be fixed.

## CI Pipeline

The GitHub Actions workflow (`.github/workflows/ci.yml`) runs:

1. **Locked dependency installation** — `pnpm install --frozen-lockfile`
2. **Documentation generation** — `pnpm docs:generate`
3. **Generated-file drift detection** — `check-stale-openapi.ts`
4. **OpenAPI linting** — `redocly lint`
5. **Route coverage validation** — `check-route-coverage.ts`
6. **Contract tests** — `check-contract.ts`
7. **Type checking** — `tsc --noEmit`
8. **Unit tests** — `vitest run`
9. **Production build** — `next build`

Breaking change detection runs on pull requests only.
