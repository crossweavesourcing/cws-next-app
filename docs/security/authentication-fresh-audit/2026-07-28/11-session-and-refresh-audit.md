## 1. Session Creation

### 1.1 Session ID Generation

`SessionService.createSession()` (`session.service.ts:125-148`) creates a session document with a MongoDB `ObjectId` as the session ID. The `ObjectId` is generated by the MongoDB driver using a cryptographically random process (12 bytes: 4-byte timestamp + 8-byte random).

The session ID is then HMAC-signed for the cookie:
```typescript
const sessionCookie = signSessionId(sessionIdStr, env.SESSION_SECRET);
```

**Finding SESS-001: Session IDs are MongoDB ObjectIds, HMAC-signed for cookie transport.**
- **Severity:** N/A (pass)

### 1.2 Device Binding

Each session is optionally bound to a device record (`session.deviceId`):
- `serverDeviceId`: The `devices._id` (ObjectId), HMAC-verified via `cws_device_token` cookie
- Device blocking check: Blocked devices cannot create new sessions
- Device identity mismatch check: Server token must match client device UUID

**Finding SESS-002: Sessions are device-bound with HMAC-signed device tokens.**
- **Severity:** N/A (pass)

### 1.3 Concurrent Session Limit

`enforceConcurrentSessionLimit()` (`session.service.ts:502-517`):
- Maximum 5 active sessions per user
- Overflow sessions are revoked (oldest first by `lastActivityAt`)
- Batch revocation: `revokeManyByIds` + `revokeBySessions` (FIX-10)

**Finding SESS-003: Concurrent session limit of 5 per user with batch revocation.**
- **Severity:** N/A (pass)

### 1.4 Refresh Token Creation

First refresh token in the rotation chain:
```typescript
const { token, tokenHash } = generateRefreshToken();
```

`generateRefreshToken()` produces 48 random bytes (96 hex chars) and its SHA-256 hash. Only the hash is stored in the database.

**Finding SESS-004: Refresh tokens are 48-byte random values, only hashes stored.**
- **Severity:** N/A (pass)
- **Rationale:** 48 bytes = 384 bits of entropy. SHA-256 hash stored server-side. The raw token is only sent to the client.

### 1.5 Account Security Version Snapshot

```typescript
const accountSecurityVersion = snapshotUser?.security?.accountSecurityVersion ?? null;
```

The session records the `accountSecurityVersion` at creation time. This enables FIX-14: defense-in-depth invalidation when the version changes (password change, security event).

**Finding SESS-005: Sessions snapshot account security version for version-based invalidation.**
- **Severity:** N/A (pass)

## 2. Session Validation

### 2.1 HMAC Signature Verification

`SessionService.validateSession()` (`session.service.ts:183-241`):
```typescript
const sessionIdStr = verifySessionSignature(cookieValue, env.SESSION_SECRET);
```

The cookie value is verified against the HMAC signature using `SESSION_SECRET`. The comparison uses `crypto.timingSafeEqual` (via `verifySessionSignature` in `crypto/token.ts`).

**Finding SESS-006: Session cookie HMAC verified with timing-safe comparison.**
- **Severity:** N/A (pass)

### 2.2 Database Lookup

After signature verification, the session is loaded from MongoDB:
```typescript
const session = await this.sessionRepo.findById(sessionId);
if (!session || session.revoked) return null;
```

**Finding SESS-007: Session validated against database, revocation checked.**
- **Severity:** N/A (pass)

### 2.3 Account Security Version Check (FIX-14)

```typescript
const currentVersion = user.security?.accountSecurityVersion ?? null;
if (
  session.accountSecurityVersion !== null &&
  currentVersion !== null &&
  session.accountSecurityVersion !== currentVersion
) {
  await this.sessionRepo.revokeSession(sessionId, 'system', 'Account security version changed');
  return null;
}
```

If the user's `accountSecurityVersion` has advanced since the session was issued, the session is revoked and rejected.

**Finding SESS-008: Security version mismatch revokes session (FIX-14).**
- **Severity:** N/A (pass)

### 2.4 User Status Check

```typescript
const user = await this.userRepo.findById(session.userId);
if (!user || user.status !== 'active') {
  await this.sessionRepo.revokeSession(sessionId, 'system', 'Account status changed');
  return null;
}
```

Disabled/suspended/deleted users have their sessions revoked on every validation.

**Finding SESS-009: Non-active users have sessions revoked on validation.**
- **Severity:** N/A (pass)

### 2.5 Idle Timeout

```typescript
const idleExpired = session.lastActivityAt.getTime() + env.IDLE_TIMEOUT_MS <= now;
```

Default: 30 minutes (`IDLE_TIMEOUT_MS`). Sessions are revoked when idle timeout is exceeded.

### 2.6 Absolute Timeout

```typescript
const absoluteExpired = session.expiresAt.getTime() <= now;
```

Default: 15 minutes (`ACCESS_SESSION_TTL_MS`). Sessions expire after 15 minutes from creation or last refresh.

**Finding SESS-010: Both idle (30min) and absolute (15min) timeouts enforced.**
- **Severity:** N/A (pass)

### 2.7 Background Activity Update

```typescript

  this.updateLastActivity(session).catch(...);
});
```

Uses Next.js `after()` to coalesce last-activity writes to at most once per 60 seconds (`ACTIVITY_WRITE_INTERVAL_MS`).

**Finding SESS-011: Activity updates coalesced to prevent write amplification.**
- **Severity:** N/A (pass)

## 3. Refresh Token Rotation

### 3.1 Atomic Replace (H-4 Fix)

`RefreshTokenRepository.atomicReplace()` (`refresh-token.repository.ts:66-85`):
```typescript
const result = await coll.findOneAndUpdate(
  { tokenHash: oldHash, replacedBy: null },
  { $set: { revoked: true, replacedBy: newId, revokedReason: 'rotated', revokedAt: now } },
  { returnDocument: 'after' }
);
```

The `replacedBy: null` predicate ensures only the first concurrent rotation wins. Two concurrent refreshes presenting the same token cannot both produce new tokens.

**Finding REFRESH-001: Atomic replace prevents concurrent rotation race (H-4).**
- **Severity:** N/A (pass)

### 3.2 Reuse Detection

If a revoked token is presented for rotation (`session.service.ts:280-295`):
```typescript
if (existing.revoked) {
  const firstReuse = !existing.reuseDetected;
  if (firstReuse) {
    await this.refreshTokenRepo.markReuseDetected(presentedTokenHash);
  }
  await this.sessionRepo.revokeSession(existing.sessionId, 'system', 'Refresh token reuse detected');
  await this.refreshTokenRepo.revokeBySession(existing.sessionId, 'reuse_detected');
  // Alert user on first reuse
  if (firstReuse) {
    this.alertingService.alertReuseDetected(existing.userId, ipAddress).catch(...);
  }
  return null;
}
```

The **entire session family** (all refresh tokens for the session) is revoked on reuse detection.

**Finding REFRESH-002: Refresh token reuse triggers full session family revocation + user alert.**
- **Severity:** N/A (pass)

### 3.3 Device Binding During Rotation

```typescript
if (session.deviceId) {
  const resolvedServerDeviceId = clientDeviceCookieValue
    ? verifyServerDeviceToken(clientDeviceCookieValue)
    : null;
  if (!resolvedServerDeviceId || !session.deviceId.equals(resolvedServerDeviceId)) {
    // Theft detected: revoke session + family
  }
}
```

If a session is bound to a device, the refresh must present the matching HMAC-signed device token. A mismatch triggers theft detection.

**Finding REFRESH-003: Device binding enforced during refresh rotation.**
- **Severity:** N/A (pass)

### 3.4 FIX-C2: Absolute + Idle Limits at Refresh Time

```typescript
const absoluteExpired =
  (sessionForExpiry.lastFullAuthAt?.getTime() ?? sessionForExpiry.createdAt.getTime()) +
    refreshTtlMs <= nowMs;
```

The refresh endpoint enforces the absolute limit (7 days from `lastFullAuthAt`) and idle limit at refresh time, preventing a refresh cookie from indefinitely extending a session.

**Finding REFRESH-004: Refresh endpoint enforces absolute (7d) and idle limits.**
- **Severity:** N/A (pass)

### 3.5 Access Session Roll-Forward

On successful refresh, the access session window is renewed:
```typescript
const accessExpiresAt = new Date(now + accessTtlMs);
const lastActivityAt = new Date(now);
await this.sessionRepo.renewAccessSession(session._id, accessExpiresAt, lastActivityAt);
```

This keeps the session alive past the original 15-minute mark as long as the client keeps refreshing (within the 7-day absolute limit).

**Finding REFRESH-005: Access session rolls forward on refresh within absolute limits.**
- **Severity:** N/A (pass)

**Finding SESS-012: Logout revokes session + refresh family.**
- **Severity:** N/A (pass)

### 4.2 Password Change

`PasswordService.changePassword()` (`password.service.ts:144-150`):

  userId,
  currentSessionId ? new ObjectId(currentSessionId) : null,

### 4.3 Password Reset

`PasswordService.resetPassword()` (`password.service.ts:205`):

ALL sessions are revoked (no exception — `exceptSessionId` is null).

**Finding SESS-014: Password reset revokes ALL sessions.**
- **Severity:** N/A (pass)

### 4.4 Account Security Version Bump

Any change to `security.accountSecurityVersion` (password change, admin security event) invalidates all sessions with the old version via the FIX-14 check in `validateSession()`.

**Finding SESS-015: Security version bump provides defense-in-depth session invalidation.**
- **Severity:** N/A (pass)

### 4.5 Device Blocking

`SessionRepository.revokeSessionsByDeviceId()` (`session.repository.ts:199-222`):

**Finding SESS-016: Device blocking immediately revokes sessions on that device.**

### 4.6 Admin Revocation

- **Single user:** `revokeAllUserSessions(userId, 'user')`

Both target only non-revoked sessions (idempotent).

**Finding SESS-017: Admin can revoke single user or global sessions.**
- **Severity:** N/A (pass)

## 5. Key Concern: Session Fixation During MFA

### 5.1 Analysis

The user-provided description mentions: "Session is not rotated after completing 2FA."

**Detailed analysis of the current flow:**

1. **Password login** → risk engine requires 2FA → `cws_2fa_pending` cookie set (NOT a session cookie)
2. **No session exists** during the MFA step
3. **2FA verification** → session is **created fresh** (not rotated from an existing one)
4. **Session cookie** is set for the first time after MFA completion

**Finding SESS-018: No session fixation vector — session is created fresh after MFA completion.**
- **Severity:** N/A (pass)
- **Rationale:** The `cws_2fa_pending` cookie is not a session. A new session with a fresh ObjectId is created only after MFA passes. There is no session to fixate because no session exists during the MFA step.

### 5.2 Pending Authentication Token Properties

The `cws_2fa_pending` cookie:
- **HttpOnly:** Not accessible to JavaScript
- **Strict SameSite:** Only sent on same-site requests
- **5-minute max age:** Short-lived
- **Opaque token:** Random 32 bytes, SHA-256 hashed for DB lookup
- **Bound to userId:** Cannot be used for a different user
- **Consumed atomically:** Single-use

**Finding SESS-019: Pending auth token is properly secured and cannot be used as a session.**
- **Severity:** N/A (pass)

## 6. Cookie Security

### 6.1 Session Cookie

- **Name:** `cws_session`
- **SameSite:** Lax (allows top-level navigation)
- **HttpOnly:** Yes
- **Secure:** Controlled by `SECURE_COOKIES` env var (required in production)
- **Path:** `/`

### 6.2 Refresh Cookie

- **Name:** `cws_refresh`
- **SameSite:** Strict (blocks cross-site form POST sends)
- **HttpOnly:** Yes
- **Secure:** Same as session
- **Path:** `/api/auth/refresh` (scoped to refresh endpoint)

### 6.3 Pending Auth Cookies

- **Name:** `cws_2fa_pending`, `cws_pw_pending`
- **SameSite:** Strict
- **HttpOnly:** Yes
- **Secure:** Same as session
- **Max age:** 5 minutes (2FA) / 10 minutes (password change)

**Finding SESS-020: Cookie security correctly differentiated by sensitivity.**
- **Severity:** N/A (pass)
- **Rationale:** High-value tokens (refresh, pending) use Strict; session uses Lax for navigation UX. All use HttpOnly and production-mandated Secure.

## 8. Recommendations

1. **Consider rotating the session ID after MFA completion** even though no fixation vector currently exists. This would provide defense-in-depth against future code changes that might create a session earlier in the flow.
2. **Monitor for refresh token reuse alerts** — a spike may indicate token theft.
3. **Consider adding session metadata** (login IP, user agent) to the session document for anomaly detection during refresh.
4. **Audit the `revokeAllUserSessionsExcept` call** after password change to verify the `exceptSessionId` is correctly derived from the current request context.
