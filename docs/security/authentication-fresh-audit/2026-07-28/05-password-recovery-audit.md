# Password Recovery Audit

## Overview

This document details the security audit of the password recovery (reset) flow in the CWS Next App, covering token generation, storage, expiry, single-use enforcement, rate limiting, enumeration resistance, session revocation, 2FA interaction, and confirmation email.

## Request Flow Analysis

### Implementation

```typescript
// src/auth/services/password.service.ts:235-273
async requestReset(email: string): Promise<void> {
  const normalized = email.trim().toLowerCase();

  // Rate limit: 5 per 15min per email
  const RESET_MAX_PER_WINDOW = 5;
  const RESET_WINDOW_MS = 15 * 60 * 1000;
  const ipAddress = await getClientIp();
  const recent = await this.loginAttemptRepo.countRecentResetRequests(
    normalized, RESET_WINDOW_MS
  );
  await this.loginAttemptRepo.recordResetRequest(normalized, ipAddress);
  if (recent >= RESET_MAX_PER_WINDOW) {
    return; // Throttled: silent return, no token minted
  }

  const user = await this.userRepo.findByEmail(email);
  const raw = user
    ? await this.tokenRepo.create(
        { userId: user._id, type: 'password_reset', payload: { email } },
        RESET_TTL_MS,  // 30 minutes
        32             // 32 bytes = 256 bits entropy
      )
    : null;
  if (raw && user) {
    const env = getEnv();
    const link = `${env.APP_URL}/dashboard/reset-password?token=${raw}`;
    await sendMail({ to: email, subject: '...', text: `...${link}...` });
  }
}
```

### Findings

#### RST-001: Reset Token Entropy Assessment

| Field | Value |
|---|---|
| Finding ID | RST-001 |
| Severity | Informational |
| Location | `src/auth/services/password.service.ts:261` |
| Evidence | `this.tokenRepo.create({...}, RESET_TTL_MS, 32)` — 32 bytes = 256 bits |
| Description | The reset token is 32 bytes (256 bits) generated by `crypto.randomBytes(32)`. This provides 2^256 possible values, making brute-force infeasible within the 30-minute window. Even at 1 billion attempts per second, it would take approximately 1.8 × 10^61 years to exhaust the search space. |
| Attack Scenario | An attacker attempts to guess or brute-force the reset token within the 30-minute window. |
| Impact | None — 256-bit entropy is well above the 128-bit minimum for security |
| Existing Control | `crypto.randomBytes(32)` (CSPRNG) |
| Remediation | None — entropy is adequate |
| Recommendation Priority | Informational |

#### RST-002: Reset Token Storage — SHA-256 Hash Only

## Reset Flow Analysis

### Implementation

```typescript
// src/auth/services/password.service.ts:162-233
async resetPassword(token: string, newPassword: string, acceptWeakPassword = false): Promise<void> {
  const tokenHash = hashToken(token);
  const pending = await this.tokenRepo.findValid(tokenHash, 'password_reset');
  if (!pending || pending.userId === null) {
    throw new Error('This password reset link is invalid or has expired.');
  }

  const userId = pending.userId;
  const strength = await this.evaluateNewPassword(userId, newPassword, acceptWeakPassword);

  const redeemed = await this.tokenRepo.redeem(tokenHash, 'password_reset');
  if (!redeemed || redeemed.userId === null || !redeemed.userId.equals(userId)) {
    throw new Error('This password reset link is invalid or has expired.');
  }

  const hash = await hashPassword(newPassword);
  await usersColl.updateOne({ _id: userId }, {
    $set: {
      password: { hash, algorithm: 'argon2id' },
      passwordChangedAt: new Date(),
      'security.forcePasswordChange': false,
      'security.lockedUntil': null,
      // ... strength metrics
    },
  });

  await this.historyRepo.record(userId, hash, 'argon2id', policy.historyCount);
  await new SessionRepository().revokeAllUserSessionsExcept(userId, null, 'user');
  await this.tokenRepo.invalidateAll(userId, 'password_reset');
  // ... confirmation email, audit log, alert
}
```

## 2FA Interaction Analysis

### Question: Does Password Reset Bypass 2FA?

| Aspect | Assessment | Evidence |
|---|---|---|
| Reset requires email access | Yes — link sent to email | `password.service.ts:267` |
| Reset bypasses password login | Yes — no password verification for reset | `password.service.ts:162` |
| Reset does NOT bypass 2FA on next login | Correct — all sessions revoked, next login goes through full pipeline | `password.service.ts:205` |
| 2FA not required for reset itself | Acceptable — email access is the authentication factor | Design decision |

**Analysis:** The password reset flow does not require 2FA because the reset link is sent to the user's email, which serves as the authentication factor. After the reset, all existing sessions are revoked, so the user must authenticate fresh — and the full authentication pipeline (including 2FA if configured) runs on the next login. This is correct behavior.

### Findings

#### RST-016: No Findings

2FA interaction is correctly implemented. Email access serves as the authentication factor for reset; full 2FA enforcement on next login.

## Overall Assessment

The password recovery flow is well-designed and implements multiple layers of security:

1. **256-bit token entropy** — brute-force infeasible
2. **SHA-256 hash storage** — database breach does not expose tokens
3. **30-minute expiry** — limits exposure window
4. **Atomic single-use** — prevents race conditions
5. **Rate limiting** — prevents email bombing
6. **Enumeration resistance** — generic responses for all cases
7. **Session revocation** — stolen sessions invalidated
8. **Confirmation email** — user notified of reset
9. **Security alerting** — reset surfaced to monitoring
10. **Password history** — prevents reuse of recent passwords

The two low-severity findings (RST-007, RST-015) are defense-in-depth improvements, not vulnerabilities.
